# 推荐与查询规则

## 使用索引

`recipe-index.jsonl` 每行是一道菜，包含标题、分类、简介、难度、原料、可选原料、特殊厨具、推荐资格、原文路径和来源 URL。使用当前 Agent 可用的文本搜索或文件查询能力搜索相关行；先按用户锚点食材、分类或菜名缩小范围，不要读取整个文件。

只把 `recommendation_eligible: true` 的记录用于推荐。查询指定菜谱时可以搜索所有记录。同名记录不得同时占据候选名额；查询遇到同名版本时列出来源差异让用户选择。

## 候选过滤

先执行严格过滤：

1. 任一必需或可选原料命中过敏原或忌口时，排除该菜谱。
2. 菜谱需要的特殊厨具未在档案或当前请求中确认可用时，排除该菜谱。
3. 用户明确指定分类、烹饪方式或其他硬条件时，排除不符合项。
4. 用户查询被过滤条件命中的指定菜谱时仍可提供信息，但必须先突出显示冲突；不要把它描述为适合用户制作。

## 排序

把用户本次明确拥有或希望消耗的食材视为锚点。按下列优先级比较剩余候选：

1. 覆盖更多锚点食材，且锚点是菜谱的必需原料而非点缀。
2. 缺少更少的必需原料；可选原料不计入缺失。
3. 在缺口相近时，利用更多用户明确拥有的非基础食材。
4. 符合用户想吃的分类、口味、难度等软偏好。
5. 三个候选在主食材或做法上有差异。

只有一个锚点时，不因可利用食材种类少而降分。不要让“只需油盐”的简单菜仅凭满足率压过真正使用锚点的菜。

## 匹配标签

- **高度匹配**：全部必需原料可用。
- **较为匹配**：通常只缺一种关键必需原料，或存在轻微条件差距。
- **补位推荐**：缺少多种必需原料或利用锚点较少，但仍满足所有硬限制。

尽量返回三个候选。高匹配不足时用较弱候选补足，并明确差距；不得用违反硬限制、依赖未确认厨具或结构不可靠的菜谱补位。

## 首轮展示

不要展开完整菜谱。每个候选只展示：

1. 菜名和匹配标签
2. 一句话特点
3. 已匹配的主要食材
4. 缺少的必需食材；没有则写“无需补充关键食材”
5. 原文提供的难度；原文提供可靠用时时才显示用时

随后请用户选择。不要在首轮复制长步骤。

## 用户选择后

先用独立小段说明该菜与当前食材、档案约束的关系，再把 `source_path` 解析为 `references/<source_path>`，读取对应原文并忠实展示。保留原文标题、必备原料和工具、计算、操作、附加内容；只跳过 HTML 注释及无法离线显示的图片行。最后附索引中的 `source_url`。

缺失项必须放在原文外，不能改写原方。只有原方提供明确份量公式时才做人数换算，并把换算结果标为独立计算结果。

## 整餐搭配

请求指向一顿饭但未说明菜数时，先问想做几道菜。用户说明后生成三个完整方案，每个方案包含指定数量的不同菜谱。

比较方案时考虑：

- 对锚点食材的整体覆盖
- 全部菜谱缺失必需食材的并集，而不是机械相加
- 主食材、做法和口味的差异
- 整体难度与用户偏好
- 无素食限制的两菜方案可对“一荤一素”轻微加分，但不得压过食材利用率或用户意图

先简要展示三个完整方案。用户选中后，分别读取并忠实展示每道原菜谱。不要扩展成周计划或声称提供医学营养方案。

## 随便推荐

没有提供食材时，从严格过滤后的推荐池中挑选三个类别或做法有差异的菜谱，并应用口味与难度偏好。提供了部分食材时按普通“有啥吃啥”排序。说明这是开放式推荐，不虚构用户拥有未声明的新鲜食材。
